# 穿搭广场与人气排行

日期：2026-08-13  
状态：已落地。不改现有四 Tab。项目中无微信 `msgSecCheck`，发布文案未接内容安全（按确认方案跳过，未半吊子接入）。

## 要解决什么

现在「分享」只有微信好友卡和复制文案，是私聊转发。  
要加的是：**可选发布到平台广场（OOTD）**，以及 **人气热门排行**。入口都在「穿搭」里，不加第五个底栏。

私人穿搭日志和公开帖必须分开：默认不公开；公开时自己勾要带照片、要带文案。

## 推荐：穿搭 Tab 两栏 + 详情里发布

穿搭页顶部分段：

`我的 | 广场`

| 栏 | 做什么 |
|----|--------|
| 我的 | 现有穿搭记录 +「今日穿搭」 |
| 广场 | 热门排行（默认）+ 可切「最新」 |

详情页现有「分享给好友 / 复制文案」保留。下面加主操作 **发布到广场**。点开后是一张选项卡，而不是保存穿搭时强制公开。

### 发布时可自由勾选

总开关：发布到广场（关掉等于撤回，私人记录还在）。

三项内容各自可选：

1. **附带穿搭照片**：有图才可勾；不勾则广场只出文字/单品卡，不露自拍或穿搭照。
2. **附带文案**：用备注，可现场改一版专门给广场的文案；不勾则广场不展示这段话。
3. **展示单品名称**：默认开。OOTD 至少要让人知道穿了什么；不勾则只有照片或文案。

三项可以任意组合。三项全关时不允许发布（会变成一张空卡）。

展示作者昵称、头像（来自账号资料）。第一期不做匿名。

### 人气怎么算

只靠 **点赞**（每人每帖一次，可取消）。  
排行：`本周` / `总榜`，按赞数，赞数相同按发布时间。  
不做浏览量、不做转发进榜，避免刷数、也避免和微信分享混在一起。

## 为什么不用另外两种

- **独立「热门」Tab**：会变成五个底栏，已经否决。
- **保存穿搭时顺带公开**：容易误发；和「自由决定带什么」冲突。必须是记录之后再发布。

## 数据（确认后给你 SQL，不直接改仓库 SQL 文件）

公开帖单独一张表，不在 `outfits` 上打公开标记：

- `outfit_posts`：作者、关联的私人穿搭 id、是否带图/文案/单品、广场文案快照、照片 key 快照、单品名快照、赞数、状态（已发布/已撤回）
- `outfit_post_likes`：`(user_id, post_id)` 唯一

快照的原因：撤回或改衣柜时，广场帖不会把别人的衣物详情接口暴露出去；私人记录删除后，已发帖可选择一并撤回。

## 接口草案

- `POST /api/ootd/posts` 从某条穿搭发布（勾选三项）
- `PUT /api/ootd/posts/:id` 改勾选或撤回
- `GET /api/ootd/feed?sort=hot|new&range=week|all`
- `POST /api/ootd/posts/:id/like` 点赞/取消
- 发布文案走微信内容安全（`msgSecCheck`），过不了不让上广场

点赞、发布按登录用户限流（比 AI 松，防刷赞）。上传后的衣物异步打标仍然不限。

## 页面

- `pages/outfit/outfit`：分段 我的 / 广场
- `pages/outfit-detail`：加发布/已发布状态
- 新页 `pages/ootd-publish`：三个开关 + 文案预览
- 新页 `pages/ootd-detail`：广场详情（别人的帖；只能赞，不能进对方衣柜）

## 不做（第一期）

评论、关注、匿名、把衣物原图公开、把私人衣柜 id 暴露给其他人。
